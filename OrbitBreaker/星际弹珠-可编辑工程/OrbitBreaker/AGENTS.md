## 2. 目标、范围和不可改约束

### 2.1 目标

三天内交付可独立运行的 **3D 弹球战斗 Demo**，一局约 3–5 分钟：玩家控制蓝色球体，在纵向弹球机战场里受持续向下重力作用，移动、向上冲刺撞击红色方块敌人、短暂吸附特定障碍、触发底部左右踏板重新弹上去，撞击高位目标得分。敌人或机关命中玩家时短暂失控下坠；达到目标分数胜利，底部漏球失败，支持重开。基础几何体美术即可；交付可执行文件、可编辑 Unity 工程、试玩说明、设计说明和测试复盘。

设计假设：**以持续下坠形成明确压力，用吸附和踏板提供恢复节奏；以可控冲刺、上冲撞击与分数反馈制造爽快感。** 测试时记录玩家是否理解吸附/踏板用途、是否主动向上进攻、失控是否有可恢复性。

### 2.2 已确认技术选型

- 实际创建版本预期：**Unity 2022.3.62f2 LTS**。先读取 `ProjectSettings/ProjectVersion.txt` 核对，不匹配则记录并确认，禁止盲目升级。
- **3D Built-In Render Pipeline**（非 URP）。不要引入 URP/Cinemachine/GAS/大型框架。
- C#、3D `Rigidbody`/`Collider`，Unity 2022 使用 `Rigidbody.velocity`，**不要使用 Unity 6 的 `linearVelocity`**。
- 第一版可用旧输入 `Input.GetAxisRaw` / `Input.GetKey`；检查 `Active Input Handling`，必要时设 `Both` 并记录。尽量无额外包依赖。
- Unity MCP 推荐用来操作 Editor、层级、资源与 Console；**MCP 不是编译/验证的唯一渠道**。若未连接，先检查插件和客户端配置；仍无法连接，则用 C# Editor 构建脚本 + Unity Editor/Batchmode 继续开发，并在日志写明未验证部分。
- 项目内 `Assets/Scripts/Editor/OrbitBreakerSceneBuilder.cs` 提供菜单 `Tools/Orbit Breaker/Build Demo Scene`，幂等生成/更新基础场景，避免依赖大量手工拖拽。

### 2.3 唯一坐标与物理约定（禁止中途混用）

- 用户于 2026-09-26 明确更正视觉方向：必须采用参考弹球机照片那样从近端斜俯视台面的 **Perspective 透视相机**，呈现近大远小、球体体积、台面厚度和光影；禁止恢复竖直正面 Orthographic 视角。战斗内部坐标暂沿用 **XY**：X 左右、Y 沿台面向远端、Z 为台面法线/厚度；该坐标约定不等于画面采用平面视角。
- 玩家 `Rigidbody.useGravity = false`，由统一物理控制器在 `FixedUpdate` 施加 `Vector3.down * gravityStrength`；冻结 Position Z，按实现需要冻结不相关旋转。
- 场地高度约20；用户于2026-09-27要求加宽，T07将可玩内宽12增至15（+25%），中央漏球口仍宽4，球体和踏板尺寸保持。左右及顶部墙体、下方左右护栏、中央漏球死亡区；底部踏板施加真实冲量。
- **单一物理写入者**：玩家的速度/力/约束由 `OrbitBreakerPlayerMotor`（或同等单一组件）协调。Dash/Magnet/Hit 只发出状态请求或力请求，禁止多个组件在同一帧争写速度。状态优先级 `Dead > Stunned > Attached > Dashing > Normal`。
- 第一版不做真正倾斜 3D 台面的复杂滚动几何，不做 HingeJoint 机械翻板，不做 NavMesh。场景仍使用 3D 模型和 3D 物理，不是 2D 游戏。

### 2.4 输入和闭环

| 输入 | 作用 |
|---|---|
| WASD | 平面方向加速度；不直接抵消下坠重力 |
| Space | 消耗1次冲刺，朝鼠标投影方向发射；吸附绕转蓄力可提高速度；每4次有效碰撞/击杀1敌补1次，最多3次，冷却1秒 |
| E / 鼠标 | 近处按E吸附，再按E脱离；鼠标绕吸附点转动蓄力，仅Space发射；超时/机关受击释放，不能无限悬停；吸附期间免敌人干扰并击退接近敌人 |
| J / K | 按住左 / 右踏板，球进入有效区时施加向上冲量，有冷却 |
| Enter | Ready → Playing |
| R | Victory / Defeat 后重开（也可在游玩中调试重开，需记录） |

敌人仅用红色 Cube：从左右/上方预设点随机刷新，向玩家移动。冲刺命中敌人造成击杀及得分；未吸附时普通接触触发一次失控并施加下坠冲量，敌人攻击须有冷却与玩家短暂无敌，避免连续多帧扣状态。失控期间玩家不可移动/冲刺/吸附，**仍受重力、墙/障碍/踏板碰撞**；踏板可在失控时救球。

T09按用户要求修订：整个Attached期间（含短暂停止鼠标绕转）免敌人攻击和物理推挤；邻近或轨道扫过敌人时向外击退，敌人闪色，无击杀/计分。脱离、超时、禁用、终局后恢复碰撞配对。墙/实体障碍和危险机关仍有效。详见D017，不要恢复T08的敌人接触脱离规则。

得分事件必须是实际交互：冲刺击杀敌人、**向上且达到速度阈值**撞击目标、触发特定高分机关。目标要有冷却或离开再触发限制，不能接触后连续刷分。达到目标分数进入 Victory；进入 OrbitBreakerKillZone 进入 Defeat；两者均冻结进一步计分/刷敌并可重开。

### 2.5 第一版参数（先通过 ScriptableObject，允许测试后调整）

`gravityStrength`、`moveAcceleration`、`dashSpeed`、`dashCooldown`、`attachDuration`、`stunDuration`、`enemySpawnInterval`、`targetScore` 共 **8 个可调参数**。T10按用户要求将attachDuration由1.5秒增加5倍为**7.5秒**，其余参数保持，见D018。敌人上限、弹板力度、碰撞阈值等先设有名称的常量；变更必须记入 `DECISIONS.md`。初始得分建议敌人 20、普通目标 50、高分目标 100；**仅为待调试值**。

### 2.6 明确不做

多角色、复杂动画、技能树、养成、多人联机、Boss、复杂 AI、真实 HingeJoint 翻板、过多敌人种类、大型框架、超出可交付能力的美术。不得为“更完整”擅自扩范围。

## 3. 多 Agent 协作规则

1. **单任务领取**：从 `Docs/TASKS.md` 选依赖已通过的一个 `READY` 任务，标记 `IN_PROGRESS`、负责人和时间。除非显式约定，不能两个 Agent 同时修改相同脚本/场景/台账。
2. **先核实再修改**：读 `STATUS`、最近交接、`git status`、`ProjectVersion.txt`、现有脚本/场景；不要覆盖用户或其他 Agent 的未提交改动。
3. **小步提交**：每完成一个任务保存场景和资源、检查 Console/编译、尽可能运行验收，再 Git commit（仓库未初始化则说明，不要擅自清理文件）。推荐提交信息 `T03: implement dash and collision`。
4. **如实标记状态**：`TODO` 未开始；`READY` 可领取；`IN_PROGRESS` 进行中；`BLOCKED` 有阻塞；`IMPLEMENTED_UNVERIFIED` 代码已写但未验证；`DONE` 满足验收且记录证据。没有 Editor / 构建环境不得写 `DONE`。
5. **MCP 操作有记录**：注明是否已连接、完成了哪些编辑器操作、Console 错误、场景是否保存。MCP 连接失败不等于项目失败，但必须记录替代方案。
6. **不虚报**：区分“写入了代码 / 编译通过 / Play 模式实测 / Windows Build 验证”。一个阶段未通过，先修复再领取依赖任务。
7. **时间盒与止损**：单个技术问题卡住约 30–45 分钟，记录复现、日志、已试办法，降级到简单可靠实现；不得牺牲闭环去追求特效。
8. **交接必须落盘**：最后 5–10 分钟更新文档；回复用户只做简短摘要并指向本地文档，不以聊天代替文档。
9. **来源与归属**：外部素材/插件/AI 生成内容记录来源、许可和用途；关键玩法与规则保持可解释可修改。

## 5. 模块边界与建议文件

- `Core/OrbitBreakerGameManager.cs`：Ready/Playing/Victory/Defeat，开始、结束、重开；不得接管具体物理。
- `Core/OrbitBreakerScoreManager.cs`：统一加分入口、通关阈值、重复触发保护。
- `Core/OrbitBreakerCombatConfig.cs`：ScriptableObject 八参数。
- `Player/PlayerStateController.cs`：状态与优先级，提供请求 API。
- `Player/OrbitBreakerPlayerMotor.cs`：**唯一** Rigidbody 速度/力写入者、XY 约束、重力、受击冲量。
- `Player/OrbitBreakerPlayerDash.cs`：输入、冷却、冲刺请求、冲刺命中资格。
- `Player/OrbitBreakerPlayerMagnet.cs`：附近 OrbitBreakerAttachmentPoint 查询、附着与释放请求。
- `OrbitBreakerEnemy/OrbitBreakerEnemyController.cs`、`OrbitBreakerEnemySpawner.cs`：红色方块追击与边缘生成。
- `Environment/OrbitBreakerFlipperController.cs`、`OrbitBreakerBumper.cs`、`OrbitBreakerAttachmentPoint.cs`、`OrbitBreakerScoreTarget.cs`、`OrbitBreakerHazard.cs`、`OrbitBreakerKillZone.cs`：单一职责。
- `UI/BattleUI.cs`：订阅状态/分数变化，不含伤害判定。
- `Editor/OrbitBreakerSceneBuilder.cs`：构建场景、组件与资源引用，必须尽量幂等。

命名可按现有工程小幅调整，但调整后要更新 `DECISIONS.md` 和任务台账中的文件路径。不要保留两套同义控制器同时生效。

## 6. 每个任务的标准执行循环

1. **读取**：本文件、台账、最新交接；检查现有文件、Git 和 Console。
2. **领取**：写入任务 `IN_PROGRESS`、负责人/会话标识、开始时间、预期修改文件。
3. **实现**：只做本任务必要改动；SceneBuilder 产物须保存到 Assets 下；对现有用户修改采取保守策略。
4. **静态检查**：核对命名空间、Unity 2022 API、引用、null、状态切换、编译错误。
5. **实测**：优先 MCP/Unity Play；其次 Batchmode 和可复现 Editor 工具。记录操作、预期、实际、日志。没有运行能力则标记 `IMPLEMENTED_UNVERIFIED`。
6. **更新台账**：结果、证据位置、变更文件、已知问题和下一任务。
7. **交接**：创建新 `Docs/HANDOFFS/...md`，更新 STATUS/CHANGELOG/TESTS；若有设计改动更新 DECISIONS；必要时提交 Git。
8. **向用户简报**：仅说本轮完成/验证/阻塞/下一步，不用复制冗长代码。

## 8. 故障排查原则

优先查看 Unity Console 的**第一条编译错误**，而不是同时修十个后续报错。区分脚本编译、Prefab 引用、Editor 工具、物理状态冲突、Play 模式现象和 Build 错误。出现球体不受控时先查是否有多个脚本修改速度、`useGravity` 是否双重施力、Z 约束及碰撞 Layer；出现漏分/刷分时检查入射速度、接触事件冷却和 OrbitBreakerGameManager 状态。记录精确复现步骤、期望、实际与修复提交，不要只写“已修复”。
